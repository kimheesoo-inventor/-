# 에이전트 파이프라인

각자의 전문 영역을 가진 6개 에이전트가 순서대로 이어받아 마케팅 캠페인을 완성합니다.
에이전트들은 독립적으로 동작하지만, **인계 규칙**을 통해 협력합니다.

```
        ┌──────────────────── 6. RSI ◀──────────────────────────┐
        │  개선 지침                                 성과·검수 결과 │
        ▼                                                       │
   0. PM ──▶ 1.리서치 ──▶ 2.콘텐츠 ──▶ 3.디자인 ──▶ 4.회의 ──▶ 5.검수 ──▶ 배포
   컨셉·전략     팩트        카피        시각화     교차 점검     승인
        └───────── 감독 ──────────┘       ▲
                                          └─ 1·2·3이 서로의 산출물을 본다
```

1~5는 한 방향으로 흐릅니다. **0번(PM)과 6번(RSI)이 그 흐름을 감싸 루프를 만듭니다.**
직선 파이프라인은 매번 같은 품질을 내지만 더 나아지지는 않습니다.
RSI가 이번의 문제를 규칙 변경안으로 바꾸고, PM이 그것을 다음 캠페인의 기준에 반영하면서
파이프라인 자체가 회를 거듭할수록 좋아집니다.

---

## 팀 구성

| # | 에이전트 | 역할 | 산출물 |
|---|----------|------|--------|
| 0 | **PM** | 컨셉·방향 설정, 전략 기획, 감독, RSI 지침 반영 | `00-brief.md` — 이후 전 단계의 판단 기준 |
| 1 | **리서치** | 시장 트렌드·산업 분석·경쟁사 동향 조사 | `01-research.md` — 핵심 팩트 + 출처 |
| 2 | **콘텐츠** | 뉴스레터·소셜 게시글·홍보 문구 카피라이팅 | `02-content.md` — 최종 문구 |
| 3 | **디자인** | 카드뉴스·썸네일·슬라이드 시각화 | `03-design/` — 이미지 + manifest |
| 4 | **전체 회의** | 3회 층위별 교차 점검, 오류를 담당 단계로 전달 | `04-crosscheck.md` — 발견 목록 |
| 5 | **검수** | 브랜드 가이드·목표 부합 여부 최종 확인 | `05-review.md` — 통과/보류 판정 |
| 6 | **RSI** | 개선사항 피드백을 규칙 변경안으로 전환 | `06-rsi.md` — 개선 지침 |

정의 파일은 [`.claude/agents/`](../.claude/agents/) 에 있고, 규칙 요약은
[`CLAUDE.md` 4절](../CLAUDE.md)에 있습니다.

## 폴더 구조

캠페인 단위로 `drafts/<슬러그>/` 아래에 쌓고, **검수를 통과한 것만** `output/<슬러그>/`로 옮깁니다.

```
drafts/2026-q3-campaign/
  00-brief.md         ← PM. 이후 모든 단계가 여기에 대조된다
  01-research.md
  02-content.md
  03-design/
    manifest.md
    card-01-hook.png
  04-crosscheck.md    ← 회의 발견 목록. 전부 처리해야 검수로 넘어간다
  05-review.md        ← 통과 판정이 나야 output/으로 이동
  06-rsi.md           ← 다음 캠페인의 규칙 변경안
```

## 이 구조가 품질을 만드는 이유

파이프라인의 핵심은 단계를 나눈 것 자체가 아니라, **각 단계가 무엇을 하면 안 되는지**를 못 박은 데 있습니다.
사람이 매번 들여다보지 않아도 오류가 다음 단계로 번지지 않게 하는 장치입니다.

### ① 사실은 한 곳에서만 생긴다
팩트는 리서치 단계에서만 생성됩니다. 콘텐츠 에이전트는 `01-research.md`에 없는 사실을
쓸 수 없습니다. 이 규칙 하나가 "문장이 밋밋해서 숫자를 하나 넣었는데 알고 보니 지어낸 숫자"라는
가장 흔한 사고를 막습니다.

### ② 못 찾은 근거는 지우지 말고 표시한다
리서치가 출처를 못 찾은 항목은 `[미확인]`으로 남겨 다음 단계로 넘깁니다.
조용히 빼면 다음 단계는 그 주장이 검증된 줄 압니다. **드러난 공백이 감춰진 공백보다 안전합니다.**

### ③ 문구는 앞 단계에서 확정된다
디자인 에이전트는 카피를 고쳐 쓰지 않습니다. 길이가 안 맞으면 직접 줄이는 대신
콘텐츠 에이전트에게 돌려보냅니다. 시각화 단계에서 문구가 조금씩 바뀌면
어느 버전이 승인된 것인지 아무도 모르게 됩니다.

### ④ 검수자는 고치지 않는다
검수 에이전트는 문제 목록만 반환하고 해당 단계로 돌려보냅니다.
**검수자가 직접 고치면, 그 수정본은 아무도 검수하지 않은 채로 배포됩니다.**
보류가 하나라도 있으면 `output/`으로 넘어가지 않습니다.

### ⑤ 기준을 정하는 자와 만드는 자를 나눈다
PM은 컨셉·타깃·핵심 메시지·성공 기준을 정하고, 직접 만들지는 않습니다.
만드는 사람이 기준까지 정하면 결과물에 맞춰 기준이 움직입니다.
`00-brief.md`에 성공 기준이 **먼저** 적혀 있어야 검수도 RSI도 판단할 근거가 생깁니다.

### ⑥ 규칙을 고칠 수 있는 것은 PM뿐이다
RSI는 개선 지침을 **제안만** 하고, 채택 여부는 PM이 결정합니다.
자기 행동 규칙을 스스로 고치는 에이전트는 매 회차 규칙이 표류합니다.
제안과 승인을 분리해 두면, 매뉴얼에 무엇이 왜 들어왔는지 추적할 수 있습니다.

### ⑦ 세 번 보되, 매번 다른 층위에서 본다
4단계 회의는 전체 오류 상황을 **최소 3회** 세부 점검합니다. 중요한 건 횟수가 아니라
**매 회차 보는 층위가 다르다는 것**입니다. 같은 렌즈로 세 번 보면 같은 것만 세 번 나옵니다.

| 회차 | 층위 | 잡히는 오류 |
|---|---|---|
| 1 · 부분 | 산출물 하나씩, 각자의 전문 렌즈로 | 근거 없는 수치, 카피와 다른 시각 자료 문구 |
| 2 · 연결 | 단계 사이 이음새 | 리서치엔 있는데 카피가 빠뜨린 논거, 단위가 바뀐 인용 |
| 3 · 전체 | 독자가 읽는 순서대로 통독 | 구성 순서, 앞뒤 안 맞는 주장, 핵심 메시지와 다른 결론 |

2회차가 특히 중요합니다. 1회차는 각자 **자기 담당 파일**을 중심으로 보기 때문에,
파일과 파일 사이 — 리서치의 값이 카피로 넘어오며 슬쩍 바뀐 지점 — 은 아무도 안 보게 됩니다.
팩트 하나를 골라 리서치 → 카피 → 시각 자료까지 따라가고 반대로도 되짚으면 그 구간이 드러납니다.

3회는 하한입니다. 발견이 0건이어도 세 회차를 다 돌고, 회차별 건수를 기록합니다.
특정 층위에서 계속 0건만 나오면 그 회차가 제 일을 못 하고 있다는 뜻이라, RSI가 그 렌즈를 고칩니다.

### ⑧ 전달은 담당자가 고칠 수 있는 형태로
발견을 넘길 때 네 가지가 다 있어야 합니다 — **위치 / 무엇이 틀렸나 / 무엇이어야 하나 / 담당 단계**.
"어색합니다"는 전달이 아닙니다. 받는 사람이 무엇을 어떻게 고칠지 판단할 수 없으면,
결국 발견자에게 되묻게 되고 그만큼 왕복이 늘어납니다.

### ⑨ 만든 사람은 자기 실수를 못 본다
초안이 다 나온 4단계에서 전체 회의를 엽니다. 리서치·콘텐츠·디자인이 각각
**자기가 만들지 않은 산출물**을 자기 전문 영역의 눈으로 훑습니다.
리서치는 카피의 근거를 보고, 콘텐츠는 시각 자료의 문구를 보고, 디자인은 카피의 분량을 봅니다.

자기 산출물을 자기가 검토하면 이미 한 번 내린 판단을 다시 확인할 뿐입니다.
교차로 봐야 "이 문장의 근거가 어디 있지?" 같은 질문이 나옵니다.

회의는 **찾는 자리이지 고치는 자리가 아닙니다.** 발견 목록만 만들고 담당 단계로 돌려보냅니다.
발견이 0건이면 0건으로 적습니다 — 채우려고 억지 지적을 만들면 반송 한도만 소모됩니다.

## 회의(4단계)와 검수(5단계)는 무엇이 다른가

| | 전체 회의 | 검수 |
|---|---|---|
| 묻는 것 | "내 전문 영역에서 볼 때 이게 틀렸나?" | "규칙에 맞나?" |
| 보는 사람 | 만든 당사자들이 서로를 | 만들지 않은 제3자가 전체를 |
| 결과 | 발견 목록 | 통과 / 보류 판정 |
| 기준 | 각자의 전문 판단 | `CLAUDE.md`와 `00-brief.md`의 명문 규정 |

두 단계가 겹쳐 보이지만 잡는 오류가 다릅니다. 규칙에는 안 걸리는데 전문가가 보면
틀린 것 — 수치가 미묘하게 다르게 인용됐다든가, 카피가 카드에 안 들어간다든가 — 은
회의에서만 잡힙니다. 반대로 개인 판단으로는 넘어갈 수 있지만 규정 위반인 것은 검수가 잡습니다.

**회의에서 이미 처리된 항목을 검수가 다시 지적하지 않습니다.** 같은 지적을 두 번 하면
반송 한도만 깎입니다. 그리고 검수까지 살아남은 오류는 RSI가 따로 표시합니다 —
그건 회의 렌즈에 구멍이 있다는 뜻이라, 다음 회차에 렌즈를 고쳐야 할 신호입니다.

## 개선 루프가 도는 방식

```
04·05 발견/보류 사유  ──▶  06-rsi.md 규칙 변경안  ──▶  PM 채택 판정  ──▶  CLAUDE.md 수정
        (문제)                    (제안)                  (승인)              (다음 회차 적용)
```

RSI가 보는 것은 "이번 결과물이 어땠나"가 아니라 **"어느 규칙이 없어서 이 문제가 생겼나"** 입니다.

- **반복 여부를 본다.** 과거 `06-rsi.md`와 대조해 같은 지적이 두 번 나왔는지 확인합니다.
  한 번 나온 실수까지 규칙화하면 매뉴얼이 금세 못 쓰게 됩니다.
- **붙여넣을 수 있는 문장으로 쓴다.** "더 신경 쓸 것"은 규칙이 아닙니다.
  가능하면 금지형으로 씁니다 — "하지 마라"가 "하라"보다 강하게 작동합니다.
- **한 건 추가하면 한 건 지울 후보를 낸다.** 매뉴얼은 매 세션 컨텍스트에 통째로 들어갑니다.
  길어질수록 개별 규칙의 힘이 약해지므로, 순증만 계속되면 루프가 스스로를 망칩니다.

## 실무에서 걸리는 함정

- **이미지 프롬프트에 텍스트를 넣지 말 것** — 생성 모델은 글자를 깨뜨립니다.
  이미지는 배경·요소만 만들고, 텍스트는 생성 후 레이아웃 단계에서 얹습니다.
- **레이아웃은 눈으로 확인할 것** — 텍스트 잘림·겹침은 코드로는 안 보이고 렌더링해야 보입니다.
- **원본을 덮어쓰지 말 것** — 이미지를 자를 때는 항상 새 파일로 저장합니다.
- **에이전트를 늘리기 전에 역할 경계를 볼 것** — 역할이 겹치면 결과가 서로를 덮어씁니다.
  4단계로 부족하다고 느껴지면 대개는 단계가 모자란 게 아니라 인계 규칙이 느슨한 것입니다.

## 실행

파이프라인 순서는 [`.claude/commands/`](../.claude/commands/) 의 슬래시 명령으로 스크립트화돼 있습니다.

```
/campaign <주제>      # 0~6단계 전체 + 게이트 강제
/brief <주제>         # 0단계 (PM 브리프)
/research <슬러그>    # 1단계
/content <슬러그>     # 2단계
/design <슬러그>      # 3단계
/meeting <슬러그>     # 4단계 (전체 회의 — 교차 점검)
/review <슬러그>      # 5단계 (통과 시 output/으로 이동)
/retro <슬러그>       # 6단계 (RSI 개선 지침)
/adopt <슬러그>       # PM 모드 5 — 채택분만 CLAUDE.md 반영
```

### 왜 슬래시 명령인가

자연어로 "캠페인 돌려줘"라고 해도 파이프라인은 돕니다. 차이는 **순서가 강제되는지**입니다.
자연어 지시는 매번 조금씩 다르게 해석되고, 급할 때 한 단계를 건너뛰기 쉽습니다.
슬래시 명령은 실행 순서와 정지 지점이 파일에 고정돼 있어 매번 같은 경로로 돕니다.

`/campaign`이 강제하는 정지 지점:

| 게이트 | 시점 | 통과 조건 |
|--------|------|-----------|
| 브리프 | 0단계 후 | 사용자 승인 |
| PM 감독 | 1~3단계 후 | `00-brief.md` 이탈 없음 |
| 회의 | 4단계 후 | 발견 항목 전부 처리 |
| 검수 | 5단계 후 | 통과 판정 (보류면 `output/` 이동 금지) |
| 반송 한도 | 회의·검수 각각 | 최대 2회, 3회째는 사람에게 |
| 규칙 변경 | 6단계 후 | `/adopt`로만 |

두 가지가 특히 중요합니다.

**반송 한도.** 검수 보류 → 재작업 → 재검수 루프에 한도가 없으면,
에이전트가 스스로 못 고치는 문제를 만났을 때 무한히 돌면서 토큰만 씁니다.
2회까지 시도하고 3회째는 사람에게 넘깁니다.

**규칙 변경 분리.** `/campaign`은 `CLAUDE.md`를 고치지 않습니다.
개선 지침 반영은 `/adopt`에서 사용자 확인을 거칩니다.
캠페인 한 번 돌릴 때마다 규칙이 조용히 바뀌면, 어느 시점부터 무엇이 달라졌는지 추적할 수 없습니다.
